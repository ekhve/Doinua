# fm1kit, the platform

**API version 43** (`FM1KIT_API` in `fm1kit/include/fm1kit.h`). The header is the contract. This page
explains it and records why it is the way it is.

## Shape of an app

```c
#include "fm1kit.h"
void app_init(void)                    { /* once, after the hardware is up */ }
void app_event(const kit_event_t *e)   { /* one call per input change */ }
void app_frame(uint32_t now_ms)        { /* ~100 times a second: draw if something changed */ }
```

The kit owns the main loop. Each pass delivers input events, then calls `app_frame`, then sends the
screen rows that changed to the LCD. Sound renders in the audio interrupt, and the key scan runs in a
10 kHz timer interrupt. Apps never see either.

## Two backends, one behaviour

- **device.c**: the FM-1, on felucca-bsp. Grown from the BSP's `hwtest`, the minimal firmware that has
  been run on real FM-1s.
- **host.c**: a PC program. It reads an input script and writes `audio.wav`, `lcd_<ms>.ppm` and
  `leds_<ms>.json`. Its script syntax is the emulator's, so a scenario runs on both.

The portable code (`core.c`, `gfx.c`, `synth.c`, `music.c`) is compiled into both, which is why the
factory can require the device's screen to equal the host's pixel for pixel.

## Decisions

| # | Decision | Why |
|---|---|---|
| D-001 | Build on **felucca-bsp + our own fm1kit**, not on a fork of all of Felucca | Felucca is a groovebox with 120 files of UI and sequencer we'd have to work around. The BSP is the hardware layer its author maintains "as a foundation for new FM-1 firmware projects". A small API of our own is easier for agents to keep correct |
| D-002 | **GPL-3.0-only** | Leaves the door open to reuse Felucca's GPL code (its 6-op FM engine, the velocity sensing) and matches the FM-1 community. The BSP-derived files stay MPL-2.0. **Confirmed by the owner, 2026-11-06 (#6)** |
| D-003 | **fm1-emu is the stand-in for the hardware** | It runs the unchanged `.fwsc`, models the screen, keys, LEDs, audio and USB, and runs at about 8× real time. A small patch (`factory/patches/`) makes it write LED levels and raw LCD frames. Worth offering upstream |
| D-004 | **A host backend with the emulator's script syntax**, and a device-equals-host screen gate | Fast checks for agents (milliseconds), with the emulator confirming the real firmware does the same |
| D-005 | **Music theory ported from Sketchpad and checked against it** (`factory/oracle/`) | Sketchpad's core is tested heavily. Its answers for every key are the reference, so the C port can't drift silently |
| D-006 | **Safety lives in device.c, out of the app's reach**: the update loader byte-identical to the pinned BSP's; the USB-MIDI update entry; the SysEx UBOOT key; OCT- + OCT+ for 5 s → update mode; two failed boots → update mode | A firmware that can't be replaced is the one unrecoverable mistake. `factory/safety.py` checks these on every build, partly by talking to the firmware over emulated USB |
| ~~D-007~~ | ~~felucca-bsp pinned at **5942e68**, the commit Felucca 1.8.2-beta ships with~~ | Replaced by D-011 |
| D-008 | Audio out as **Q15 << 7** (24-bit right-justified, -6 dBFS ceiling) | What Felucca does: its notes say the codec ran clean at -18 dBFS. `<< 16` clipped (found by the first emulator run) |
| D-009 | Package identity **FM-1_1301** | What installers see. Distinct from Felucca (9xx) and hwtest (12xx) |
| D-010 | Updates allowed on flash parts **0x856014 and 0xB36014** | As Felucca 1.8.2-beta does. **Not tested on hardware**: the newer part's testing is still pending upstream |
| D-011 | felucca-bsp moved to **78cf51b** (`main`, 2026-11), the update loader re-pinned | The newer BSP fixes a boot-guard bug our device.c had copied from hwtest (felucca-bsp#17: a non-`volatile` record let the compiler drop the check, and **the first boot after an install landed in update mode**; the emulator can't show it because its RAM starts zeroed). | D-012 | **Flash writes limited to two regions**: the update staging area (0xE0000–0xE5000) and fm1kit's store (0x93000–0x97000, D-022) | felucca-bsp's `FM1_FLASH_WRITE_REGIONS`: the flash driver refuses anything else, so a bug in an app or in fm1kit can't erase the boot area, the app, or another firmware's saved data |

Found by the pitch gate |
| D-014 | **API 1: sounds are an engine and a preset**; the six Felucca-Engines are engines 1–6, the kit's own tones engine 0 | One way to pick any sound, so apps and the factory can step through all of them (`app-host --list-sounds`). No per-preset effects yet (the presets' FX sends are ignored) |
| D-015 | **The host simulator models the device's output chain**: MASTER at 900 (where the emulator rests it) and the −6 dB ceiling | Found by the engines scenario: every device level was 0.44× the host's. Now host and device levels agree within a few percent |
| D-016 | **CPU gate**: every sound with 8 voices held stays under 75 % interrupt load on the cycle-modelled emulator | Over 100 % a real FM-1 would glitch. Heaviest today: Organ wheel FULL ORGAN at 56 % |
| D-017 | **Velocity from the keys' carbon pills**: the scan reads a held key with its row driven (felucca-bsp's analog rows, as fm1-velocity, CS-1 and fm1-ctl do); a press waits for two readings (≤ 12 ms) and its strongest one maps to 1..127 through a curve measured on the emulator's pill model (CS-1's measurements of a real FM-1).
